## D2 数据模型与一致性

### D2-1【P1·增长】列表查询 = 每行多个相关子查询，无分页窗口
- 证据：`requirement_repo.py:58-73`（每行 3 个相关子查询：clarify_item×2 + test_case×1，`ORDER BY created_at DESC` 全量）；`iteration_repo.py:15-31`（每行 5+ 个：clarify×2、case×1、`design_final_json LIKE`×1、gate EXISTS×2 + MAX 子查询，再叠加关联子查询 JOIN `_REQ_JOIN`）；`task_repo.py:34`（`LIMIT 100` 有窗口但无翻页参数——`services/task.py:63-68` 已因该窗口被迫改用 `exists_by_type` 直查）。
- 触发：需求 × 用例增长后，迭代/需求列表页、`/api/tasks` 查询线性劣化；clarify_item 无 `(req_id,status)` 复合索引，answered 计数子查询逐行过滤。
- 方向：①列表 SQL 改 JOIN + GROUP BY 聚合或一次批量 IN 查询；②`clarify_item(req_id,status)`、`task(status)` 补索引；③需求/任务列表加分页或游标参数（可先只加 LIMIT 上限防御）。
- 风险/验收：键序与数值口径不变；verify-*.mjs 回归。

### D2-2【P1·增长】启动迁移每次全量跑，无 schema 版本账本
- 证据：`migrations.py:96-109`——每次启动 `executescript` + 逐列 PRAGMA 判列 + 全部回填函数；`_backfill_case_no`（`migrations.py:124-141`）每次启动执行 `SELECT … JOIN … WHERE case_no IS NULL` 全表扫 + `SELECT MAX`；`_backfill_clarify_status`（:117）每次执行 UPDATE（条件不中时无写入但语句照发）。幂等正确，但无「已应用版本」记录，成本随库大小线性。
- 方向：引入一张 `schema_version` 账本表，已应用步骤跳过；判列补列保持现状。
- 风险：迁移逻辑本身动刀需演练存量库（report P3 批次做）。

### D2-3【P2】gate 域中文状态值 + JSON 列 LIKE 推导
- 证据：`schema.sql:21-22`（gate_round.status 默认 '待裁决'）、`gate.py:108/195/199/212`（'待裁决'/'已放行'/'落改'/'驳回'/'存疑'/'待执行'/'已执行'）；其余域全英文（submitted/clarifying/queued…）。`iteration_repo.py:22-25` 用 `design_final_json LIKE '%"skipDeclared"%'`、`LIKE '%"finalized"%'` 推导 design_phase——JSON 文本格式一旦变化（序列化器/键序）静默失效。
- 方向：gate 域值改英文枚举 + 前端映射中文（需数据迁移与 verify-gate 断言同步改）；design_phase 推导改 `json_extract` 或落显式列。
- 分歧项：⚠ gate 中文值疑为「skill 权威两值落库」刻意对齐上游——**需用户裁决**（见 §4）。

### D2-4【P2】循环体内逐条写/查（违反自家 CLAUDE.md 规约）
- 证据：`services/requirement.py:170-172`（重推澄清项：`delete_by_req` 后 `for c in parsed: insert(c)` 逐条插）；`requirement.py:195-196`（`missing_media` 在列表推导内逐个 `media.exists()` 查库）；`services/case.py:102-104`（同步删除：`for cid in stale_ids: delete + delete_by_case` 逐条）。对照：`case.py:78-79` 的 `allocate_case_nos` 批量分配已示范正确做法。
- 方向：`db` 层加 `executemany`；media 存在性改一次 `IN` 查询；删除改批量语句。
- 风险：低（行为等价，事务边界不变）。

### D2-5【P2】JSON 列读写口径不统一，无 Schema 演进手段
- 证据：`models.py:34-40` `string_list` 兜底降级；`TestCase.verify_ref_list()`（models.py:230）有 helper 但 `CaseListRow.verify_refs` 直接存 list（models.py:249）；`domains/target_repos/checks_json/baseline_json/design_final_json/content_json` 各处自行 `json.loads` + 各自的坏值降级（`requirement.py:454` suppress、`design.py:181-187` `_parse`、`gate.py:355` `_parse`——三份同构降级函数）。读取端无法约束内容形状，新增消费方各自防御。
- 方向：统一 JSON 列编解码入口（repo 层或 models 层一对 helper），content_json 类「外部产物」保留宽松降级但集中实现。

### D2-6【P3】软删子表数据成永久孤儿；媒体文件无生命周期
- 证据：`services/requirement.py:42-58` 软删只打标 requirement，clarify_item/artifact/test_case/media 行与 media 文件原样保留（刻意：可恢复）。但无任何清理/归档策略，软删数据与 media/ 目录只增不减。
- 方向：不急于动；记录为增长边界项（备份体积、media 目录孤儿检测可先做只读巡检脚本）。

### D2-7【P3】时间戳口径：本地时间字符串 + 无时区，消费端硬编码东八区
- 证据：`common.py:44-49`（`Times.now()` 本地时间）；前端 `time.js:4`、`TaskPanel.vue:293` 与 `runner/runner.mjs:242` 均硬编码 `+08:00` 解析。服务器/浏览器任一不在东八区即显示错乱（当前单机部署无感）。
- 方向：维持库内格式（契约），但在 README 记录「部署约定：服务器时区必须 Asia/Shanghai」或后端出参补 ISO 时区字段（属契约变更，需裁决）。

### D2-8【P2·实测】SQLite 非 WAL、无 busy_timeout
- 证据：`db.py:26` 连接仅设 `check_same_thread=False, isolation_level=None`；实测 `PRAGMA journal_mode` → `delete`。单连接 + RLock 内安全；但任何外部进程并发访问（backup 脚本、IDE 浏览库、verify 期间）都会 `SQLITIC_BUSY` 且无重试窗口。assistant.db 的问题见 D5-1（更严重）。
- 方向：`PRAGMA journal_mode=WAL` + `busy_timeout=5000`（对单连接模型无副作用，WAL 文件多两个副本需进 .gitignore/备份考量）。

## D3 业务逻辑与领域模型

### D3-1【P2】状态机守卫分散，无集中流转定义
- 证据：requirement 状态规则散落——`set_status`（requirement.py:277-283，submitted→reviewing→clarifying）、`push_artifacts`（:104 published 拒推）、`publish`（:264 仅 clarifying）、`set_answer`（:240 仅 clarifying）、`task.create_guarded`（task.py:77 发布终态锁 + `_post_publish_task` 豁免表）、`put_draft`（task.py:187-190 同一豁免表第二份实现）、`gate.open`（gate.py:80 仅 published）。终态锁豁免口径在 task.py 两处靠注释「与 create 的豁免口径一致」人工对齐。
- 方向：抽一个 `states.py`（或 requirement 状态机模块）：集中定义合法流转表 + 发布终态锁豁免函数，各守卫点引用同一常量源。不改任何文案与行为。
- 风险：纯重构，pytest/verify 全量回归即可。

### D3-2【P2】require 404 守卫四份复制
- 证据：`requirement.py:361-365`、`design.py:174-178`、`gate.py:348-352`、task.py 内联同构检查（task.py:71-74）——同一段 find+404 四处维护。
- 方向：下沉到 `RequirementRepo.require(req_id)`（仓储层抛 404）或共享 helper；服务层保留可读入口名。

### D3-3【P2】魔法值字面量散布（status/type/level 无常量集）
- 证据：`'clarifying'` 全仓 20+ 处直书；task type 有 `T_*` 常量（task.py）但 requirement status、clarify status、draft type、gate verdict 各自裸字符串。tests 锁行为，但拼写错误只能靠运行发现。
- 方向：与 D3-1 的 states.py 一并收口；前端 `disposition.js` 已是良好示范（前后端唯一判定源注释）。

### D3-4【P3】乐观锁仅覆盖用例域
- 证据：test_case 有 version 谓词更新（`case.py:92`、tests 锁定）；`clarify_item.set_disposition`（clarify_item_repo.py:36-40）、`requirement.set_status` 等均无版本——并发双开页面作答会静默互相覆盖（last-write-wins）。内网单人场景可接受，多人协作时澄清作答是高频并发点。
- 方向：分歧项——是否给 clarify_item 补 version 属契约变更（需裁决，见 §4）。

### D3-5【亮点确认】L2 编排与任务通道的可靠性设计
- `orchestration.py:36-69` 双段独立容错（收尾失败不阻断排队）；`task_repo.claim`（task_repo.py:44-58）条件 UPDATE 原子领取；`loop.py:92-99` claim 与发布间终态竞态兜底。此部分无需优化，列为回归保护对象。

## D4 接口契约与安全

### D4-1【P0·安全】`GET /api/tasks/next` 写语义走 GET，绕过写令牌
- 证据：`routers/tasks.py:31-39`（领取任务=写操作，方法 GET）；`main.py:104-118` token_guard 仅拦「非 GET 且 /api/」。`tasks.py:3` 注释自称「写端点统一 /api 前缀（X-Token 写保护覆盖）」——next 不在其列。启用 `SDLC_WRITE_TOKEN` 的部署下，未授权方 GET 一次即领走队头任务（任务悬死至超时恢复；反复 GET 可阻塞整条流水线）。另有浏览器预取/爬虫误触发面。
- 方向：改 POST（需同步 runner.mjs:255 与 AgentLoop 调用方），或 token_guard 对 `/api/tasks/next` 特例加鉴权。属行为变更，需与 runner/verify 脚本联动改（见 §3 批次 1）。

### D4-2【P0·安全】媒体按存储 MIME 同源渲染 = 完整存储型 XSS 链
- 证据：`routers/media.py:32-37` 以落库 MIME 直接响应，无 `Content-Disposition: attachment`、无 `X-Content-Type-Options: nosniff`；上传端 `_safe_mime`（services/media.py:88-91）仅校验格式不设白名单，`text/html` 可入库。消费端 `DocBlock.vue:100/114` 与 `DocBlock.vue:697` 附件 `target="_blank"` 直开。前端 SPA 与 API 同源托管（main.py `_mount_static`）→ HTML 媒体同源执行脚本 → 在默认无鉴权（write_token 空）下可调任意写 API（删需求、发布、领任务）。上传面包括 agent `upload_media` 工具（tools.py:175-193，内容源自外部文档抓取——非完全可信输入）。
- 方向（低成本高收益）：媒体响应统一加 `Content-Disposition: attachment`（图片 MIME 白名单内联）、`X-Content-Type-Options: nosniff`；上传 MIME 白名单化。不改变合法图片/附件的展示（`<img src>` 不受 Content-Disposition 影响）。

### D4-3【P1·安全】媒体上传无大小上限，请求体全量进内存
- 证据：`routers/media.py:20` `await request.body()` 全读；`services/media.py:31-34` 仅校验非空。无类型白名单、无字节上限——大包直接内存+落盘双放大。
- 方向：设上限（如 20MB，413）+ 流式或先查 Content-Length；MIME 白名单与 D4-2 合并处理。

### D4-4【P2】契约三处手工对齐，无 OpenAPI
- 证据：路由全部返回 `dict[str, Any]`（FastAPI 自动 docs/openapi.json 为空壳）；契约 = `docs/DEV-PLAN.md`（手写）+ `schemas.py:30` `_WIRE` 键序（手工）+ 前端肉测，三处需人肉同步。
- 方向：出参 pydantic response_model（字段声明序=键序，逐字节兼容可验证）→ 自动 OpenAPI → 前端生成类型（见 §3 批次 2）。D1 子代理的文档漂移比对结果将补充本条证据。

### D4-5【P2】HTTP 语义小瑕疵
- 证据：`DELETE /api/iterations/detail?name=`（iterations.py:56-59）删除目标走查询参数；`GET /api/fr-points`（requirements.py:69-71）必填 `req_id` 查询参数却没有 400 校验（`fr_points` 服务里 `require` 只验需求存在）——`req_id` 缺省时 `find("")` 返回 404 文案「需求不存在：」。可接受但不够整洁。
- 方向：随批次 2 契约工作一并处理或保持现状（低优先）。

### D4-6【P3】错误信息内漏内部细节
- 证据：`services/media.py:56` 落盘 OSError 直出；`routers/assistant.py:73` SSE error 事件 `f"{type(e).__name__}: {e}"`。内网可接受，公网化前需收敛。

## D5 运行时与可靠性

### D5-1【P1】assistant.db：每请求新连接 + 无锁并发写（推演，两并发会话可复现）
- 证据：`routers/assistant.py:62` 每次聊天 `SqliteChatSession(...)` 内 `sqlite3.connect`（agent/assistant.py:206）且从不显式 close（靠 GC）；该库无 RLock、无 WAL、无 busy_timeout（同 D2-8）。SSE 流期间 `add_items` 写入（assistant.py:221-232）——两个并发会话/同一会话两条并发消息即 `database is locked` 异常，直进前端 error 提示。与 platform.db 的单写者模型刻意隔离（注释），但隔离库没有隔离出安全，反而丢了锁保护。
- 方向：assistant.db 套用与 `Database` 相同的连接复用 + RLock（或至少 WAL + busy_timeout + 单连接），显式管理生命周期。

### D5-2【P1】AgentLoop 主循环异常退出后永久停摆，无自愈无告警
- 证据：`agent/loop.py:83-88`——非 Cancelled 异常仅 `log.exception` 后 `_alive=False`，循环结束不重启。一次意外（如 claim 时 DB 瞬时错误）= 进程内通道死亡直到人工重启；仅 `/api/agent/status` 可见 running:false，无人主动盯。
- 方向：异常退避重启（如 30s 退避拉起）或至少 status 端点置 degraded 语义 + 启动日志醒目化。

### D5-3【P2】助理 SSE 无服务端 deadline
- 证据：`routers/assistant.py:64-76` `Runner.run_streamed` 无超时包裹（对照任务通道 executor.py:96-97 有 `asyncio.wait_for(…, remain)`——双通道不同标准）。模型端挂死则 SSE 连接与模型调用悬住直到客户端断开。
- 方向：套 `asyncio.wait_for` 或依赖底层 SDK 超时配置，与任务通道对齐。

### D5-4【P2】双执行通道三处平行实现（口径漂移风险）
- 证据：①自检逻辑两份——runner.mjs:182-211 `selfCheck` vs `agent/loop.py:134-172` `self_check`（注释自称「自 runner.mjs 逐条移植」，已见细微措辞差异，判定口径目前一致）；②启动恢复两套——runner.mjs:237-247 逐条 API vs `loop.py:71` 走 `expire_stale` bulk（task_repo.py:103-108）；③超时默认值两处配置（TIMEOUT_MIN vs agent_timeout_min）。D1 子代理将给出 prompt 模板重复度全量对照。
- 方向：平台侧出「自检规则表」端点或共享描述文件，双通道消费同一规则；恢复统一走服务端 bulk（runner 不再自扫）。

### D5-5【P3】stop/lifespan 细节
- 证据：`loop.py:44-51` stop 吞一切异常（注释声明尽力而为，可接受）；`main.py:43-53` lifespan 启动 AgentLoop 失败会阻断整个服务启动（agent 配错拖死 API——是否符合预期需确认）。

## D6 前端应用质量

### D6-1【P0·bug】409 冲突明细是死代码——`e.data` 永远 undefined
- 证据：`src/api.js:9` 抛 `new Error(data.error || …)`，Error 对象**不携带** `.data`；`TaskPanel.vue:240` `if (e.data?.conflicts)` 永假 → conflicts 横幅（:415-419）与「覆盖平台版本」按钮（forceCases）永远不出现，用户只见 toast「登记失败：版本冲突，批次未应用」，无法自助裁决。乐观锁 409+conflicts 的后端能力被前端截断。
