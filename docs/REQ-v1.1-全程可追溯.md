# 需求文档：SDLC 产物协作平台 v1.1 —— 产物全程可追溯（连贯性改造）

> 版本：v1.1 ｜ 状态：待实施 ｜ 需求提出：平台使用者（单人维护者，向团队分发）
> 交互基准：`claude-sdlc-skills/platform-demo/index-v11.html` + `data-v11.js`（已由需求方验收的交互原型，本文档与其冲突时以本文档为准，并同步修正 demo）
> 实施范围：平台后端 + 前端 + sdlc-sync skill 契约 + 验收脚本。**本文档不含实现方案**，字段与契约要求是"必须达成什么"，不是"如何达成"。

## 0. 背景与目标

### 0.1 平台现状（v1.0，已上线）

平台承载两个公共产物域：**需求质检**（原始需求 → 质检三件套 → 澄清闭环 → 标准需求文档）与**测试用例登记**（用例注册表，双来源：sdlc-test 推送 / 表单提交）。架构铁律（不可违反）：

- 本地 markdown 是**工作权威**（六个 sdlc skill 的内部消费链不经过平台）；平台是**共享权威与交互面**。
- 桥 = 平台 REST API + `sdlc-sync` skill，全手动触发。
- 两个产物域的初始数据已在平台上：真实需求「区域教学技能比赛」（31 条澄清问题、96 条需求点、42 条用例）。
- v1.0 的已知形态问题（本文档要解决的）见 §0.2。

### 0.2 需求方反馈的四个断层（改造动因）

v1.0 平台上所有环节存的都是"关于原文的**转述 + 定位**"，而**原文本体只在飞书**。引用链每一环都断在平台边界上：

| # | 断层 | 表现 |
|---|---|---|
| 1 | 原始需求在外部 | 原始需求 tab 只有一个飞书链接；看 digest/体检/澄清的任何人，每一条都要跳出平台去飞书找上下文 |
| 2 | 需求点不知来源 | 需求点注册表只有"编号+简题"，看不出每条从原文哪一段拆出、为什么这么拆 |
| 3 | 体检有出处无内容 | 体检问题带"原文定位"（如 详述6.8.5），但定位是引用符号不是内容，读者无法判断问题本体 |
| 4 | 标准文档错位 | v1.0 的"标准需求文档" = digest + 澄清结论表合订，是**裁决记录**视角；需求方要的是**需求定稿**——消解全部未决点、可直接交给开发测试当依据的完整需求陈述 |

### 0.3 总目标（一句话）

**平台上每一条信息都能回答"你从哪来"，并且一键到达**——引用不许是死文本：凡出现出处、定位、关联编号的地方，必须可点击、可定位、可回跳。此原则对需求域与用例域同等适用。

## 1. 已确认的设计决策（需求方拍板，不可推翻）

| # | 决策 | 语义 |
|---|---|---|
| D1 | **原文全文快照上台** | 平台存原始需求的全文 markdown 快照。语义钉死：**快照 = 质检与澄清的依据版本**（最新修订以飞书为准）；每次推送产物时刷新快照并更新时间戳；**发布后冻结**（实质变更须新开一轮质检）。快照是只读副本，绝不成为第二需求权威 |
| D2 | **需求点按出处分组** | 需求点注册表不再平铺：**出处在前、需求点在后**——组头为原文出处小节（如「§7.2 修改比赛」），组内挂该段原文拆出的需求点 |
| D3 | **功能点地图 ↔ 需求点双向索引** | 两者是互补维度（页面/模块视角 vs 原文规则视角），不合并为一张表；每个需求点标注归属功能模块（module），功能地图每行显示关联的需求点编号，双向可达 |
| D4 | **体检/澄清统一需求域分组** | 两 tab 使用同一份**全局需求域顺序**（本需求为 7 域：修改比赛 → 状态机与流转 → 术语与命名 → 查询与展示口径 → 评审与颁奖规则 → 数据与字段 → 覆盖与文档质量；顺序是常量，跨 tab 一致），组内按 🔴→🟡→🔵 排序 |
| D5 | **体检 ↔ 澄清一一对应、双向跳转** | 澄清问题与体检问题同源 P 编号、一一对应；两个 tab 的每条都挂对方跳转入口，点击切 tab + 滚动 + 闪烁高亮 |
| D6 | **标准需求文档 = 重写版** | **以原始需求全文快照为底稿**（需求方 2026-09-18 澄清：非 digest 摘要视角，digest 区块仅作章节组织索引，原文规则全集必须等价承载），把体检定论与已答复澄清结论**逐条消化合入正文**（✅ 标记定案处；结论与原文冲突时以结论为准，原文表述废弃处理），❓ 消除、废弃条款以删除线+定案说明呈现；未答复项按假设口径保留并标 ⚠️；澄清结论表**降为附录**保留裁决可追溯。目标口径：**开发拿这一份文档即可开工、AI 读这一份即可获得需求的全貌（规则全集）、边界（范围/不做/假设）与逻辑（状态机/矩阵/校验链），无需回飞书**（合成规范见 sdlc-sync `references/standard-doc-spec.md`） |
| D7 | **引用全部可点击** | 全平台凡出现 `FR-xx`、`体检.Pxx`、`需求.Axx`、`Pxx`、出处/定位、覆盖判定的地方，必须可点击并到达目标（tab 切换 → 滚动定位 → 高亮/闪烁）。定位不到时必须**诚实提示**（说明原因），不得静默失败 |
| D8 | **安全语义接受** | 全文快照会使飞书文档的权限被复制（平台无登录、内网可达者均可见）。需求方已知悉，接受对策：内网部署 + 127.0.0.1 默认绑定 + 预留写 token + 快照只读 |

继承不变的红线（v1.0 已有，本改造不得破坏）：缺陷与执行结果不上平台（§4.4 有细化裁决项）；复验后人工触发推送；重推产物按 seq 保留平台已答复内容；本地 md 永远是工作权威。

## 2. 交互规格（需求域，按 tab）

> 以下行为均已在交互原型中实现并验收，描述粒度即可照做。通用跳转交互规范（D7 的落地形态）：
> **跳转 = 切换 tab → 滚动至目标 → 高亮/闪烁（约 2.2s 后消退）**；定位失败 = 顶部 toast 诚实说明原因（如"当前快照为节选，未包含……；真实环境为全文快照，可直接定位"）。

### 2.1 原始需求 tab

- 渲染原文**全文快照**（markdown 渲染）。
- 顶部横条三要素：快照时间戳、依据版本语义（"本快照是质检与澄清的依据版本；最新修订以飞书文档为准"）、打开飞书文档的链接。
- 横条必须注明：重推产物时快照同步刷新；发布后冻结。
- 无快照时（历史数据）回退为链接形态，并提示"快照将由 sdlc-sync 首次推送生成"。

### 2.2 结构化 Digest tab

自上而下：需求概述 → 涉及角色 → 功能点地图 → 需求点注册表 → digest 原文折叠。

1. **功能点地图**（角色×页面/模块，⭐=本期范围）：
   - 每行新增**出处/覆盖**列：出处（如 详述6.1）可点击 → 跳原始需求快照并高亮对应原文段；覆盖薄弱的行（⚠️）必须挂对应体检问题跳转（如 体检.P26 ↗）。
   - 每行新增**关联需求点**列：按 module 双向索引（D3），显示该模块下全部需求点编号 chips。
2. **需求点注册表**（D2）：
   - 按**出处分组**渲染：组头 = 出处小节名（含该组需求点计数），组内行 = 编号 / 简题 / 行级出处 / 归属模块。
   - 组顺序按原文小节出现顺序（§7.1 → §7.7，内部再按出处细分，如 §7.4 查询拆为管理列表 / 教师广场 / 参赛记录 / 初审与作品列表 / 区管复审 / 专家任务）。
   - 每行带锚点（data 属性），供标准文档的 FR 引用跳转定位（§2.5）。
   - **需求点行可见"被哪些用例覆盖"**（用例域反向索引，见 §4-R1）。
3. **digest 原文折叠**：展示快照级 digest markdown（含 §8 假设清单）——它是标准文档中「需求.Axx」引用的定位落点；跳转到来时自动展开并高亮目标假设行。

### 2.3 体检报告 tab

- 顶部三色统计保留（🔴/🟡/🔵 计数）。
- 明细按**需求域分组**（D4），组头显示：域名、该组问题数、红黄蓝分布；组内按级别排序。
- 每条问题：
  - 出处（原文定位）**可点击** → 跳原始需求快照定位；
  - 有**原文摘引**（quote）的渲染为引用块，摘引头带"在快照中定位 ↗"；
  - 挂「澄清 Pxx ↗」跳转（D5）；
  - 保留处理状态/去向（✅已确认 / ⭕待复核 / 跳过）。
- 摘引是新增数据（v1.0 的 ≤20 字短引不够用）：由 sdlc-sync 结构化时从原文提取**完整冲突原文**（平台侧无 20 字限制）；无摘引的条目允许为空。

### 2.4 澄清清单 tab

- 分组、组序、组内排序与体检报告**完全一致**（D4）——需求方明确要求两 tab 可对照阅读。
- 横条声明与体检的一一对应关系（同源 P 编号）+ 答复进度条。
- 每条问题：出处可点击定位；摘引引用块；挂「来自体检.Pxx ↗」回跳；PM 答复交互不变（澄清中可改、失焦保存、发布后只读）。
- 全部答复后提示由 sdlc-sync 执行 pull + publish（不提供平台侧发布按钮——发布是本地重算后的动作）。

### 2.5 标准需求文档 tab（重写版，D6）

- **内容结构**（sdlc-sync 合成时遵循，细则见 `references/standard-doc-spec.md`）：元信息头（编号/迭代/合成时间/质检依据快照时间/答复进度）→ 概述与边界（含本期范围与不做、术语、角色职责）→ **以原文全文快照为底稿**、按业务域组织的定稿规则正文（原文规则全集等价承载，消化全部已答复结论与体检定论，✅ 标注定案处；废弃条款以删除线+定案说明呈现；状态机/矩阵/校验链等逻辑载体文本化）→ 遗留假设（⚠️ 标注，需求.Axx）→ **附录：澄清结论表**（裁决记录，降为附录）。
- **引用链接化**（D7 的核心场景）：渲染后自动将文中四类引用转为可点击——
  - `FR-xx` / `需求.FR-xx` → 切到 Digest tab，定位高亮需求点注册表对应行；
  - `体检.Pxx` → 切到体检报告，高亮该问题；
  - 附录裸 `Pxx` → 切到澄清清单，高亮该问题；
  - `需求.Axx`（假设）→ 切到 Digest，**自动展开原文折叠**，定位高亮假设清单该行。
- 顶部横条声明重写版语义 + "全文引用可跳转"。

### 2.6 全局需求域顺序

需求域顺序是**平台级常量**，体检与澄清两个 tab（以及未来用例域的分组，见 §4）共用；本次为 7 域（见 D4），不同需求的域集合可以不同（由 sdlc-sync 推送时给定），但**同一需求内全局唯一、顺序固定**。

## 3. 数据与契约要求（字段语义，实现方式由实施任务定）

全部新增字段**必须可选**（向后兼容，旧数据不迁移也可用，仅缺少对应展示）。

| 字段 | 语义 |

|---|---|

- push-artifacts payload：新增 `snapshot:{md}`；`digest.fr_points[]` 增 source/group/module；`audit.items[]` 增 quote/group；澄清 `items[]` 增 quote，theme 变为必填。
- publish 的合成物语义变更为重写版（D6），payload 不变（standardMd）。
- `references/payload-schema.md` 必须同步更新；`evals/` 中自动化脚本补断言。
- **约束**：重推按 seq 保留平台已答内容的既有守卫逻辑不得回归。

## 4. 测试用例域的同等追溯要求（本次新增诉求）

需求方明确：用例域要实现**同款关联跳转**。以下关联关系基于 cases.md 的真实结构推导，按优先级列出；R1–R4 为本期必须，R5 为开放裁决项。

### R1（必须）用例 ↔ 需求点，双向

- 现状：用例已携带关联需求点（points）。
- 要求：① 用例列表/详情中的需求点 chip 可点击 → 跳 Digest tab 定位高亮该需求点行；② 需求点行（注册表）显示"被哪些用例覆盖"（用例编号 chips），可点击跳到用例详情。
- 验收：任选一个需求点，两跳内看到"覆盖它的全部用例"；任选一条用例，一跳看到它关联的需求点原文上下文。

### R2（必须）用例 ↔ 体检问题，双向

- 依据：cases.md 的「重点验证项」表天然记录了 体检.Pxx ↔ 用例 的关联（如 体检.P06→TC-33、体检.P15→TC-13、需求.A2→TC-12）。
- 要求：体检问题行显示"关联用例"（编号 chips，可点击跳到用例详情）；用例详情显示"重点验证"引用（可点击回跳体检问题）。
- 数据需求：用例 payload 增加可选的"验证引用"字段（体检.Pxx / 需求.Axx 编号列表，来自 cases.md 重点验证项表）；体检侧关联由平台从用例数据反推计算，不要求双向冗余存储。

### R3（必须）标准文档 → 用例覆盖（两跳可达）

- 要求：标准文档正文点 `FR-xx` → 需求点行（已实现于需求域）→ 该行可见覆盖用例（R1 的反向索引）。不要求标准文档内直接内联用例编号。
- 验收：从标准文档任一定稿规则出发，两跳内看到验证它的用例。

### R4（必须）用例行的缺陷编号引用（注意：不是缺陷上链）

- 现状：cases.md 缺陷跟踪表记录 BUG-xx（缺陷本身不上平台，红线不变）。
- 要求：用例详情/行可展示该用例产出的缺陷**编号引用文本**（如 `BUG-02（R1·待修复）`）——它是"用例的产出物引用"，不是缺陷数据上链；缺陷的完整生命周期仍留在 cases.md。点击行为：提示"缺陷留在本地工作区 cases.md"（不做缺陷详情页）。
- 理由：需求方的追溯诉求覆盖"这条用例发现了什么"；不做详情页即不违反红线。

### R5（开放，需求方裁决后生效）执行轮次摘要是否上平台

- 背景：v1 红线"执行态不上平台"的理由是执行真实发生在本地、平台上无真实写入来源的状态必然腐化。但追溯视角下，"这条用例跑到哪一轮、结论如何、证据在哪"是自然的关联诉求。
- 选项：A. 保持不上（执行信息完全留本地）；B. 只读轮次摘要随用例推送（如 `R1 通过（附 BUG-02）`、`17/42 已执行`，来自 cases.md，sdlc-sync 推送时快照化，不做平台侧编辑）；C. 完整执行记录+证据上链。
- 本文档不裁决。实施任务在 R1–R4 完成后向需求方呈报此选项，**不得默认实施**。

### 用例域交互规范

跳转交互（切 tab → 滚动 → 闪烁/高亮）与需求域完全一致；用例列表的筛选（迭代/需求/状态/来源/搜索）保持不变。

## 5. 验收标准

### 5.1 交互验收（对照 demo 逐条人工）

1. 原始需求 tab：快照全文可见，横条含时间/语义/飞书链接三要素。
2. Digest：功能地图每行出处可点定位、覆盖薄弱行挂体检跳转、关联 FR chips 正确；注册表按出处分组（组头/计数/行级出处/模块）；任一需求点行可被标准文档 FR 引用定位。
3. 体检：7 域分组且组序为全局常量序；组内级别排序；有摘引条目可定位快照；每条可跳澄清。
4. 澄清：组序与体检一致；每条可回跳体检；答复交互与发布只读不回归。
5. 标准文档：重写版结构完整；四类引用点击全部正确跳转并高亮；假设引用自动展开原文折叠。
6. 用例域：R1–R4 的跳转与展示全部可用。

### 5.2 自动化回归（平台仓 scripts/，断言需扩展）

- `sync-real.mjs`：新字段回读断言（快照落库、fr 的 source/group/module、quote 可选性、体检 group 分组正确）。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| 工作权威 | 本地 markdown 文件，skill 消费链的事实源；平台内容均可由其再生 |
| 依据版本 | 原文快照的语义：质检与澄清所针对的那一版原文，非最新版 |
| 需求域 | 对需求的问题/条目按业务域的聚类（本需求 7 域），平台级分组常量 |
| 需求点（FR） | digest 规则表产出的带编号规则条目（需求.FR-xx），追溯外键 |
| 需求点注册表 | 平台上需求点的分组登记视图（按出处分组） |
| 摘引（quote） | 从原文提取的完整冲突/依据原文片段，渲染为引用块 |
| 双向索引 | 功能模块 ↔ 需求点的互相可达关系（D3） |
| 重写版 | 消化全部已答复澄清结论后的需求全文（标准文档形态，D6） |
| 裁决记录 | 澄清结论表：每条问题"怎么定案的"（重写版的附录） |
