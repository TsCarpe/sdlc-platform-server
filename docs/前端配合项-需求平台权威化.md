## 2. 核心概念速览（前端视角）

- **块模型**：原文 = 扁平块数组（一行一块），`{id, type, text, ...attrs}`。`type ∈ title|heading|
  paragraph|list-item|table-row|image|attachment|whiteboard`（**comment 块只在导出时拼回，不可提交**）。
  块 `id` 即锚点：飞书源 = 飞书块 ID；平台新发 = `blk-` + 26 字符 ULID（如 `blk-01M4TX871H...`，总长 30）。
- **派生字段不提交**：`path`/`ordinal`/`comments` 是读时推导/拼回的，编辑器提交前须剥掉。
- **attrs 中的 None 值会归一**：提交时 `parent: null` 与省略 `parent` 键等价（服务端剥 None 比较）。
- **changed 态**：已发布需求确认变更单后的中间状态——大量通道关闭（见 §6 守卫表），前端要有明确态展示。
- **澄清两族**：`origin ∈ skill|incremental`（机器 P 系：`P1`…）| `local`（评论升级 L 系：`L01`…），
  列表出参已带 `origin` 键（区分呈现）；L 系行计入发布守卫「澄清全处置」。
- **变更单 kind**：`change`（人提）| `reconcile`（迁移对账，未发布卡 confirm 不转 changed）|
  `rebaseline`（放行一次全量质检）。

## 3. 后端已就绪的 API 契约

全部端点详见 `docs/openapi.json`（60 路径）。下面是前端要新接的面（形状=实测契约）。

### 3.1 原文读面（已有，编辑器数据源）

```
GET /api/requirements/{id}/doc.json
→ {"blocks":[{id,type,text,...attrs}], "media":[{id,name,mime,bytes,sha256}]}
```
块数组含拼回的 comment 块（`{id,type:"comment",ref,anchorBlockId,thread,reactions,path}`）——
**编辑器提交前必须过滤 `type==="comment"` 的块**。空表时 404（原文未导入）。

### 3.2 块级编辑（窗口 1 · 未发布卡，v4-7）

```
POST /api/requirements/{id}/blocks/diff        # dry-run 预览（不落库）
PUT  /api/requirements/{id}/blocks             # 应用
body: {"updatedBy":"<手填身份，必填>", "blocks":[<全量块数组>]}
→   {"items":[{"blockId","op":"edit|insert|delete|move","oldText","newText",
              "oldAttrs":{}|null,"newAttrs":{}|null,"moved":true?}],
     "counts":{"edit":n,"insert":n,"delete":n,"move":n}}
```

规则（前端必须遵守的提交契约）：
- **全量块数组**：提交编辑后的全部内容块（保持文档序）；消失的块 = delete（软删）。
- **新块 id**：留空或任意临时 id（服务端发 `blk-` 平台 ID，响应 items 里 insert 项的 `blockId`
  即新 ID——**保存后必须重拉 doc.json 刷新本地锚点**）。
- **已有块 id 不得改动**；提交里出现已软删的 id → 409 基线过期（提示刷新）。
- **parent 拓扑**：`parent` 引用的块必须在本批之前出现；表格行（table-row）的行内子块
  （attrs.parent 指向该行）必须紧跟该行（或紧跟其同父子块）。
- 删列表父项时子项须**上提**（parent 清空/改指 + depth-1）后提交，否则 400。
- 幂等：同数组重发 → items 空、零写入。
- 预览与应用同守卫同 diff；保存成功后建议重拉 `doc.json` + `GET /api/requirements/{id}/changes`
  （如果该卡有变更单，编辑入口不同——见 §6）。

### 3.3 评论（v4-8）

```
POST   /api/requirements/{id}/comments                      # 建评论
body: {"blockId":"", "author":"", "text":"必填", "replyTo":null}
→ 单行视图 {"id","blockId","origin":"platform","externalId","author","text",
            "replyTo","resolved":bool,"createdAt"}
GET    /api/requirements/{id}/comments
→ {"comments":[...同上...], "unresolvedCount": n}
POST   /api/requirements/{id}/comments/{cid}/resolve        # {"resolved": true|false} 线程级
DELETE /api/requirements/{id}/comments/{cid}                # 单条物理删（回复行保留）
POST   /api/requirements/{id}/comments/{cid}/escalate       # 升级澄清项
body: {"level":"yellow 可选", "theme":"评论升级 可选"}
→ {"seq":"L01","level","theme","question":"<评论文本>","quote":"<块文本>","anchor":"<块ID>",
   "status":"pending","origin":"local","srcCommentId":<cid>}
```

- `blockId` 空 = 卡片级评论（挂卡片头部「整体疑问」区）；非空锚定原文块（含软删块——照常锚定）。
- resolve 是**线程级**（目标行归根 + 回复链全置同值）；已解决评论仍可升级（escalate 不改 resolved）。
- **重复升级同一评论 → 409**「每条评论只可升级一次」。
- 列表页角标：`unresolvedCount`。
- 飞书导入评论同管道（`origin:"feishu"`，`externalId` 非空），呈现统一。

### 3.4 变更单（窗口 2/3 · 已发布卡，v4-11~17）

```
POST   /api/requirements/{id}/changes                # 人提 draft（body 同 PUT blocks + 元信息）
POST   /api/requirements/{id}/changes/reconcile      # 对账入口（kind=reconcile|rebaseline，系统单）
body: {"kind":"reconcile 可选","title","detail","proposedBy":"必填","blocks":[全量数组],
       "comments":[{externalId,blockId,author,text} 可选]}
GET    /api/requirements/{id}/changes                # 列表（含 kind/status/abortedBy/confirmedAt）
GET    /api/requirements/{id}/changes/{cid}          # 详情（items + counts + impact?）
PUT    /api/requirements/{id}/changes/{cid}          # 反复保存（仅 draft；items 全量重算）
DELETE /api/requirements/{id}/changes/{cid}          # 仅 draft 可删
GET    /api/requirements/{id}/changes/{cid}/impact   # 影响面预览（现算不冻结）
POST   /api/requirements/{id}/changes/{cid}/confirm  # body {"confirmedBy":"必填", "impact"?}
POST   /api/requirements/{id}/changes/{cid}/abort    # body {"abortedBy":"必填"}（LIFO 仅最新单）
```

详情/保存响应形状：

```json
{"id":7,"reqId":"REQ-…","kind":"change","title":"…","status":"draft|confirmed|aborted",
 "proposedBy":"张三","confirmedBy":"","abortedBy":"","createdAt":"…","confirmedAt":null,
 "items":[{"blockId","op","oldText","newText","oldAttrs":{},"newAttrs":{}}],
 "counts":{"edit":1,"insert":1,"delete":1,"move":0},
 "impact":{…仅 confirmed 单：冻结影响面…},
 "contentRev":1}
```

impact（预览与冻结同形状）：

```json
{"changeId":7,"status":"confirmed",
 "blocks":["fs-p1","fs-tr1","fs-trc1"],            // 受影响块集
 "sections":[{"headingId":"fs-h1","path":"背景"}],   // 章节（heading block_id，禁 seq）
 "clarifyItems":[{"seq","level","question","status"}],
 "frPoints":[{"id":"需求.FR-01","name":"…"}],
 "cases":[{"id":"TC-1","title":"…","frPoints":["需求.FR-01"]}],
 "digestRows":[{"kind":"feature|flow|state","anchor","summary":"角色·模块：功能"}],
 "counts":{"blocks":3,"sections":1,"clarify":2,"frPoints":1,"cases":1,"digestRows":2}}
```

confirm 语义要点（UI 文案对齐）：应用块表 + content_rev+1 + published→changed + **受影响澄清重开**
（旧答复挪 note 前缀「因变更单#N 重开，原答复：…」，PM 需重新处置）；`body.impact` 可携带
确认界面人工增删后的完整影响面对象（缺省=机械预览值）——**确认界面必须展示 diff + 四类清单**。
abort = 全量逆向回滚（块表回原状、pending 澄清恢复），条件见 §6。

### 3.5 增量质检（v4-14，任务通道）

confirm 成功后 L2 自动排 `incremental_check` 任务（`createdBy:"auto:change-confirmed"`，任务列表
现有 UI 直接可见）。产物草稿 `incremental_bundle` 的**采纳界面**是前端要做的新面：

```
GET  /api/requirements/{id}/drafts/incremental_bundle   # 草稿（contentJson = 增量包）
POST /api/requirements/{id}/drafts/incremental_bundle/approve   # body {"by":"采纳人"}
→   {"ok":true,"changeId":7,"mergedBy":"…","removedRows":n,"newRows":n}
```

增量包 contentJson 结构（渲染采纳预览用）：`{changeId, sections:[heading blockId],
digestRows:{features,flows,states,auditItems,frUpserts,frRemoves}, invalidate:{digestAnchors,auditIds},
clarify:{items}, summary, riskTier}`。采纳=服务端机械合并（区间整组替换），建议预览 =
受影响章节 + 新旧行对照 + 作废清单。规范文本：skills 仓 `sdlc-intent/references/incremental-guide.md`。

### 3.6 其他增量端点（既有面的新数据）

- `GET /api/requirements/{id}`：card 加 `contentRev`；items（澄清）行加 `origin`。
- `GET /api/requirements/{id}/gate`：`change` 加 `reqChangeIds:[变更单号]`（GR-3 横幅点入用）。
- 任务端点不变（`GET /api/tasks?req_id=`）。

## 4. UI 需求清单（按优先级分期）

### P0 · 编辑器（窗口 1 · 未发布卡）——方案 C 块级聚焦编辑（DESIGN-v4 §14）

**交互规格**（设计定稿，勿自行升级为富文本）：
- **渲染态**：块列表照常渲染（复用 OriginTab/DocBlock 现有渲染：行内 markdown 样式、图片、评论角标）。
- **块手柄**（hover 出现）：拖拽排序（HTML5 原生 drag&drop，**不引 dnd 库**）、「+」插入兄弟块、
  菜单（升级/降级 heading level 与列表 depth、删除、块类型转换）。
- **单块编辑态**（点击进入，Esc/失焦保存退出），按类型分控件：
  | 块类型 | 编辑控件 |
  |---|---|
  | paragraph / list-item | textarea（markdown 文本，自动增高）+ 工具条按钮插行内语法（选中点 B 包 `**`） |
  | heading | 级别选择 + 文本输入 |
  | table-row | 行表单（head + cells 数组，整块替换） |
  | image / attachment | 上传替换（`POST /api/requirements/{id}/media?name=&mediaId=`，块引用新 mediaId） |
  | whiteboard | 只读（平台外产出再替换） |
- **输出契约**：编辑器组件输出**全量块数组**（§3.2 提交契约）——窗口 1 直接编辑与变更单 draft
  **共用同一组件**，仅提交端点不同（`PUT …/blocks` vs `POST/PUT …/changes`）。
- **保存流**：调 `POST …/blocks/diff` 预览 → 展示四态 diff（可跳过）→ `PUT …/blocks` →
  重拉 doc.json 刷新锚点（insert 块拿到服务端发的 blk- ID）。
- **重新质检按钮**：保存后入口「质检已过期，重新质检」→ `POST /api/requirements/{id}/tasks
  {"type":"quality_check"}`（无专用端点——人工创建即重新质检）。

**明确不做**（§14.2，防承接方过度发挥）：整篇连续编辑（不引 contenteditable）、行内所见即所得、
多选/批量块操作、保存后的事务级 undo（撤销=会话内浏览器原生 + 前端块操作栈；保存后回退=
重推前次内容）。演进路径：Tiptap（Vue 3）留作后期，数据层不动换编辑面。

## 5. 状态 × 通道矩阵（前端可用性判断）

| 通道 | submitted/reviewing/clarifying | published | changed |
|---|---|---|---|
| 块级直接编辑（PUT blocks） | ✅ | ❌ 409 终态锁 | ❌ 409（入口=变更单 draft） |
| 评论 / resolve / escalate | ✅ | ✅ | ✅（随时可发） |
| 澄清作答 | clarifying ✅ | ❌ 409 | ✅（面对重开+新增项） |
| quality_check 任务 / digest_bundle 草稿 / 全量重推 | ✅ | ❌ 终态锁 | ❌ 409（**rebaseline 未消化单例外**） |
| standard_doc 任务 / standard 草稿 | clarifying ✅ | ❌ | ✅ |
| 变更单 draft 建议与保存 | ✅（不限状态） | ✅ | ✅ |
| 变更单 confirm | ❌（仅 reconcile 单豁免：应用+保持原状态） | ✅ | ✅（串行：前序未消化 409） |
| 变更单 abort | ❌ | ❌ | ✅（仅最新 confirmed 单） |
| 发布 | clarifying ✅ | — | ✅ 双重守卫（见下） |
| 开闸（gate/open） | ❌ | ✅ | ❌（==published） |

**changed 发布双重守卫**（前端预检提示）：①存在未消化变更单 → 提示先完成增量合并；
②必须有 standard 草稿且提交的 `standardMd` 与草稿**逐字节一致**（哈希比对）——发布入口应
改为「从草稿预览发布」（预览即草稿内容，提交同一份文本），不要让用户手改发布内容。

## 6. 守卫错误面 → UX 映射

后端 409/400 文案是契约（verify 黑盒按文案断言）。前端**按关键词分流**，不要全文匹配：

| 场景 | 判定关键词 | UX |
|---|---|---|
| 编辑基线过期 | 「已被后续修改」「基线过期」 | 提示刷新原文（重拉 doc.json），本地未保存改动告知丢失风险 |
| 编辑×质检互斥 | 「质检任务」+「编辑」 | 提示等质检完成；给任务列表跳转 |
| 删除父块留子块 | 「未在本批之前出现」「父块缺失」 | 编辑器内高亮问题块，提示上提或连删 |
| 行内子块不紧随 | 「必须紧随其表格行」 | 拖拽约束（前端预防）+ 报错回显 |
| changed 拒全量 | 「全量…已关闭」「rebaseline 变更单例外」 | 引导走变更单/增量通道 |
| 串行 confirm | 「未消化」 | 提示先完成增量质检合并（给任务/草稿入口） |
| 发布草稿不符 | 「与最新草稿不符」 | 改走草稿预览发布流 |
| 重复升级评论 | 「只可升级一次」 | 禁用按钮（escalate 前查 L 行是否已有该 srcCommentId——answers 已带） |
| 放弃 LIFO | 「LIFO」 | 仅最新单渲染 abort 按钮 |
| 乐观锁（用例 409） | `conflicts` 键 | 既有惯例（CaseList 已有） |

## 7. 实施注意事项（后端实施中踩过的坑）

1. **insert 的 blk- ID 由服务端发**：保存响应 items 里拿新 ID 后必须重拉数据；编辑器会话内
   引用（如新行内子块的 parent）在提交前用临时 id，服务端自动映射改写——但**第二次保存要带
   服务端已发的 blk-**（沿用不漂移）。
2. **提交前剥键**：`path`/`ordinal`/`comments`（派生）与 `type:"comment"` 块；`parent:null`
   可省略键。
3. **L 系行计入发布守卫**：评论升级未处置会堵发布（澄清全处置含 L 行）——前端在发布预检里
   把 L 行与 P 行同权提示。
4. **changed 下的读面**：`doc.json` 反映已应用的变更块（diff 展示用 `changes/{cid}` 的 items，
   不要自己 diff doc.json）。
5. **时间戳秒级**：所有 `*_at` 字段是 `%Y-%m-%d %H:%M:%S` 本地时间字符串（字典序可排序）。
6. **impact/sections 一律 heading blockId**：任何「章节区间」的本地缓存都不要存 seq 数值
   （整体重排会改写全表 seq）。
7. **发布流改造**（changed 分支）注意 clarifying 老流不动（无草稿前置直推 standardMd 仍是
   契约——verify-m2 锁死）；只对 `card.status==="changed"` 走草稿预览发布。
8. **编辑器与变更单共用组件**的分支点只在提交动作：窗口 1 = `PUT blocks`（即时生效）；
   变更单 = `POST/PUT changes`（draft，confirm 才生效）。守卫差异见 §5。

## 8. 验收判据（对应后端黑盒已锁行为）

- 编辑 → 重拉 doc.json：改动生效、软删块不渲染、评论随宿主块。
- 编辑后「重新质检」→ 产物 anchor 落在编辑后块集（blk- 新块可被锚定）。
- L 系行经重推不丢（后端保证），前端呈现 origin 区分。
- 变更单 confirm → 卡片变 changed、澄清重开可见 note 前缀、GR-3 横幅带单号（放行过的卡）。
- 增量采纳 → digest 视图刷新、changed 下可发布（草稿一致流）。
- 全程 `npm run lint` + `npm run test`（vitest）绿；联调后端 `scripts/verify-all.sh` 不因前端
  改动红（前端不入后端 CI 面，但同源部署后手工冒烟）。
